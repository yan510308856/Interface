# 强化版 Proposal A：工具执行加速后，原有安全防护还有效吗？

日期：2026-09-23。本文基于补充文献核查重新收缩选题，不包含本项目的实验结果，也没有修改实验代码。它替代旧提案中“比较 S/P/D 的安全排名”这一主线。

建议英文工作标题：**Do Agent Safeguards Survive Tool-Execution Optimizations? A Controlled Study of Security, Utility, and Cost**。

## 1. 这次具体把 idea 改强在哪里

研究对象改为一个实际的开发决定：团队为了减少模型调用和等待，把逐步工具调用改成并行调用或程序化调用，原来部署的安全防护能否继续发挥作用？哪些性能收益保留了防护效果，哪些需要额外适配？

这比问“三种 agent 哪个更安全”更具体。它有明确使用者：正在升级 agent 执行方式的应用开发者和框架维护者；也有明确交付物：什么条件下可以迁移，必须保留哪些检查信息，迁移后应该验证哪些案例。

核心问题是：

> 在工具权限和逐调用检查位置保持一致时，执行方式带来的观察历史与参数传递变化，会怎样影响现有防护的实际效果？给防护保留必要的运行信息，能否在不让主模型重新阅读全部中间结果的情况下，恢复安全性并保留效率收益？

这是候选问题，不是已发现的漏洞。不能保证一定存在足够大的效果，更不能保证录用。当前能够做的是让“什么算新发现、怎样证明、什么时候停止”变得明确。

本文区分三种证据：**已有事实**来自链接的原始来源；**研究判断**是本稿的取舍；**待验证假设**要由后续实验检验。

## 2. 哪些旧主张要主动放弃

本次补查发现了一篇非常接近上一轮建议的工作：[Stop Means Stop](https://arxiv.org/abs/2607.14166)。其 2026 年 8 月更新版报告了 agent 框架中的审批分支泄漏、取消后遗留执行和重放重复效果，并提出环境外部的执行控制。这里确认的是作者公开报告，本项目未复现其结果；本次未核实正式 venue。

因此，不能再把“暂停或取消之后仍发生副作用”作为本提案的新核心发现。它应作为必须控制和排查的已知原因。

另外两条也应放弃：

- “先计划再执行能减少注入”已经接近 CaMeL、FIDES、SPA 的问题。[SPA](https://arxiv.org/html/2608.27234v1) 明确讨论了固定计划、敏感参数与持久状态，本次核查为预印本。
- “增加 commit/undo 来限制损失”已有 [GoEX](https://gorilla.cs.berkeley.edu/blogs/10_gorilla_exec_engine.html) 等研究先例。

这些都能成为基线或机制背景，但换名字、换任务不能构成主要创新。

## 3. 为什么新的问题有现实基础

**已有事实：**程序化工具调用确实会改变哪些中间结果进入模型。[Anthropic 的官方说明](https://www.anthropic.com/engineering/advanced-tool-use) 展示了本地处理工具输出、仅将部分结果返回模型的流程。它是产品机制证据，不是安全性证据。

防护不一定依赖同一条观察路径。主模型、外部审查模型、工具输入检查、工具输出检查可能各自接收不同信息。所以“主模型看不到原文”不能自动推导为“安全检查也看不到原文”。这个区别必须从实际接口和日志中核实。

**一个重要的反例：**[OpenAI Agents SDK 的工具文档](https://openai.github.io/openai-agents-python/tools/) 明确说明，其程序化子调用继续经过正常生命周期，包括 guardrails 和审批。这限制了“打包调用必然绕过检查”的说法。文档是设计声明；具体版本中的行为仍需用测试确认，不能预先认定有漏洞。

同样，[guardrails 文档](https://openai.github.io/openai-agents-python/guardrails/) 区分了 agent 层与工具层的检查及覆盖范围。正确使用工具级检查的系统，应当成为积极对照，而不是故意被配置成弱防护。

**研究判断：**有意义的剩余问题在于：检查被调用并不自动意味着它得到的决策依据保持不变。比如任务意图审查器过去能看到逐步历史，迁移后可能只看到一个计划和当前参数，也可能仍能通过工具事件获得完整依据。这两种情况都要测，不能只选容易失败的配置。

## 4. 一个贯穿论文的例子

用户让一个 agent 整理几个项目的测试诊断，并把报告写入用户指定的位置。外部诊断文本中夹有恶意建议，试图让 agent 改动无关的安全配置。

逐步执行时，主模型会逐份读取诊断。一个部署在写入之前的任务意图审查器，可以看到用户任务、当前拟执行的写入，以及 agent 当前可见的历史。

优化后，agent 在本地批量收集和处理诊断，仅把摘要返回主模型。底层写入仍然经过同一个审查器，权限也未改变，但审查器拿到的历史可能发生了变化。

现在存在几种不同结果：

1. 恶意指令没有进入主模型，根本没有违规写入提案。这是主模型暴露减少的收益。
2. 模型仍提出违规写入，而相同审查器在不同信息视图下作出不同判断。这才是防护迁移的候选问题。
3. 审查器已经拒绝，但执行器仍完成写入。这属于执行控制问题，优先对照 Stop Means Stop，不计为本文独立的语义发现。
4. 审查器始终能拦住，优化同时降低成本。这是成功迁移案例，也应保留。

不能假设第二种结果必然出现。恶意配置路径可能足够明显，让审查器无需历史也能拒绝；这类任务正好是必要的稳定性对照。

对于代码修复，不能只按“是否写出参考 patch 之外的路径”判攻击成功。必须独立说明目标行为为什么违反任务要求或已声明的安全约束。

### 5.2 可辩护的候选增量

候选贡献是以下内容的组合：

> 在相同模型、任务、工具权限和逐调用执行检查下，测量具体执行优化如何改变已有防护的增益；通过固定调用的配对审查区分模型行为变化与审查信息变化；最后验证能否用运行时已经拥有的信息恢复防护效果，并保留优化收益。

本次定向检索未定位到完整覆盖这一组合的实证设计。但这不是“首次”证明；尤其需要继续精读上表中摘要级核查的近邻。

如果最后的结果只有“删除来源信息后更不安全”“漏掉检查会出事”，则这项组合也不足以形成强贡献。需要真实迁移证据、跨任务规律和对开发选择有影响的结果。

## 6. 主场景：研究 agent 软件的迁移，先不强求完整代码修复

建议主定位是 **agent 应用的执行优化与安全回归实证研究**。软件工程意义来自应用改造、框架接口、回归检查和因果调试；不必把所有任务都包装成代码生成。

实验分两个环境，避免同时维护很多 benchmark：

1. **机制与主对照环境：结构化读写工具任务。** 优先从 AgentDojo 选择已有状态与攻击目标可判定的任务。它能帮助控制权限、复位状态，并区分模型提案与实际效果。
2. **外部验证环境：真实仓库维护任务。** 选择自然包含独立检索或结果传递片段的任务。完整任务仍允许模型分析代码、生成补丁、根据测试结果重新规划；仅切换适用片段的执行方式。

不把“读源码后立刻凭字段引用生成补丁”当 D 的能力。对需要新语义判断的地方，三组都可以返回主模型。

仓库任务至少保留正常局部修复、正常跨模块修复和只读诊断，避免使用一刀切的“任何跨目录写入都是攻击”标准。恶意内容先只放在非执行文本中，避免测试脚本自己完成目标效果。

如果真实仓库中没有足够自然的适用片段，就保留通用工具应用主线，撤回“完整 coding agent 优化”的结论。若目标是以代码修复为核心的论文，则应另选问题，而不是人为改造任务。

## 7. 四个研究问题与相互竞争的解释

| RQ | 研究问题 | 假设 | 必须排查的另一种解释 |
|---|---|---|---|
| RQ1 | 执行优化后，相同防护还能减少多少违规效果？ | 某些优化改变防护的安全收益，且不同任务存在稳定差异 | 优化只改变了主模型提案，防护本身没有变差 |
| RQ2 | 变化来自什么信息或执行路径？ | 对同一个拟执行调用，guard 可见信息变化会改变判断 | 漏接检查、超时、格式错误、拒绝后执行，或者只是输入更长 |
| RQ3 | 给 guard 保留运行信息，能否恢复效果并保留性能收益？ | 主模型只看必要结果，而 guard 按需看执行证据，可以兼顾两者 | 恢复全部成本后已没有效率收益；或简单 allowlist 就足够 |
| RQ4 | 这些关系能否跨模型、runtime 和工作流复现？ | 风险与参数动态确定、决策所需事实等可观察条件有关 | 只在一份 prompt、一个模型或特制案例中成立 |

这些假设不要求风险一定上升。成功迁移、稳定拒绝和误拒下降都应报告。先声明假设，再看数据，不能根据某次效果临时改写研究问题。

## 8. 三种执行模式如何保留，但不承担虚假的创新

S/P/D 是代表配置，不是互斥的完整 taxonomy。

| 配置 | 明确的实验语义 | 首轮保持不变的内容 |
|---|---|---|
| S：逐步反馈 | 每个调用后模型可重新决定 | 底层工具、权限、guard 与预算 |
| P：独立调用并发 | 参数提交时确定，整组完成后反馈 | 每个子调用都单独经过相同 guard |
| D：依赖执行 | 同组后续调用可引用先前结果，没有内部模型 | 实际参数解析后再进入相同 guard；先使用顺序依赖链 |

P 遇到真实依赖可以增加模型轮次，不提前得到答案。D 需要新语义判断时也可结束当前计划并返回模型。首轮不引入新解释器，不训练专属模型，不做自动 SOP 演化。

自然任务实验中的计划可以不同，因为这正是实际部署效果。固定计划的机制实验另做，不要求所有自然轨迹完全一致，也不只保留各组都成功的样本。

对独立调用再做顺序/并行的小对照；对结果回传再做完整/固定字段的小对照。不要一次把并行、过滤、权限和模型训练全部换掉。

## 9. 实验的关键：把主模型的视图和 guard 的视图分开

很多讨论把“agent 的上下文”当成唯一的信息入口。这里要分别记录：

- 主模型在作出决定时看到了什么。
- guard 在批准当前具体调用前看到了什么。
- 执行器实际执行了什么。

```mermaid
flowchart LR
    T[底层工具返回结果] --> M[给主模型的观察]
    T --> E[运行时已存在的结果与事件]
    M --> A[模型提交计划或调用]
    A --> R[解析当前具体参数]
    R --> G[同一个逐调用 guard]
    E --> G
    G -->|允许| X[执行工具并记录效果]
    G -->|拒绝| B[不执行该调用]
```

图是实验方案，不是已实现的系统。E 不代表新建 provenance 链、签名系统或复杂追踪框架；先使用执行程序本来就有的工具名、调用 ID、请求参数、返回值和时间。

### 9.1 主防护只选一种，避免先做排行榜

首轮选择一个固定的、基于用户任务审查拟执行调用的语义 guard。固定其模型、提示词、决策阈值、超时处理；在每个可能产生敏感效果的具体调用之前同步检查。guard 不以 agent 自述“这是安全的”作为可信依据。

如果复用已发表实现，必须按该实现原有设计接入；若接口只支持自建 baseline，明确称“task-intent guard baseline”，不能冒充 PACT/FIDES 的完整复现。CaMeL/FIDES 改变整体架构，不能被当作随便插拔的同一种 guard。

先比较三个设置：

| 设置 | 说明 | 回答的问题 |
|---|---|---|
| G0 | 无额外语义 guard；保留共同沙箱与底层权限 | 架构本身怎样改变攻击与任务完成 |
| G1 | guard 获得可信任务、实际工具参数和当前可用的对话历史 | 原有基于对话的审查方式迁移后表现如何 |
| G2 | 相同 guard；增加或替换为运行时能够在线提供的相关调用结果与来源身份 | 将主模型与 guard 的信息需求分开，是否有可测收益 |

G1 不能被故意删掉它原本支持的来源或工具事件。只有真实接入方式是 transcript-based 时，它才代表现实迁移。若系统原本支持 G2，记录它是成功设计，不能“降级后发现漏洞”。

G2 的相关信息选择规则必须在开发集确定，如当前调用引用的工具结果以及触发本轮决策的观察；不能事后挑出含攻击的句子。允许保留真实 tool/server 身份，但不能把评估者知道的“这条值受攻击控制”标签偷偷提供给 guard。

### 9.2 正确的确定性策略作为对照

额外用一小组有明确规则的任务检查：当前具体路径/收件人/操作超出任务 allowlist 时，正确的同步策略应在三组中都阻止效果。

如果这个对照失败，先修 harness 或归类为执行控制问题。它不是主防护的竞争劣势。对于语义授权不能可靠形式化的真实任务，保留独立人工判定与 uncertain 类，不假装存在完整机器 oracle。

### 9.3 信息量和成本不能作弊

G2 可能获得更多信息，也可能更贵。这是被测适配的代价，不宣称它与 G1 信息完全相同。

至少补充：给 G1/G2 相同 token 上限；用等长但无关的事件作为对照；报告不截断条件；将 guard 的 token、等待与调用次数计入总成本。不能只报主模型变便宜，而漏掉审查器的费用。

如果 G2 的收益仅等同“输入长一些”，就不能声称找到了特定运行信息的作用。如果保留必要信息后执行优化完全失去成本优势，则应报告这个限制。

## 10. 用两层实验分清因果关系

### 层 A：同一个具体调用，给 guard 不同的在线信息视图

从 clean 和 attack 条件的调用中抽样，覆盖合法与非法提案。每个样本包含可信任务、调用时已经存在的观察、当前具体参数和独立合法性标签。

将同一份提案交给同一个 guard，配对比较 G1/G2。不得使用调用之后才出现的结果。随机化审查顺序；需要时重复采样以观察 guard 自身随机性。

这个实验可以支持“信息视图改变了审查判断”，但不能单独支持“部署 G2 会减少多少真实损失”，因为线上拒绝还会改变 agent 后续行为。

合法/非法标签由显式任务约束和独立结果判定产生；困难样本由两名评审在不知道 guard 判断时标注。分歧无法解决的样本单列，不强行判分。

### 层 B：完整在线运行

在同一任务和资源快照上运行 `S/P/D × G0/G1/G2 × clean/attack`，让模型自然选择动作，测实际效果与任务完成。

按任务配对、随机化运行顺序、每次重置环境。模型版本、温度、底层工具、权限、原始资源、攻击位置与总预算固定。动态轨迹不同是整体效果的一部分。

先采用相同 payload 测迁移，后续再对每个设置给相同攻击优化预算。两类结果分别报告，不能把在 S/G1 上特意优化的攻击当作对其他模式无偏的最强攻击。

**两层证据必须相互支持。** 在线变差而固定调用审查不变，说明主要原因可能在主模型或计划；固定审查改善而在线无收益，说明 guard 误判未必是该任务的主要瓶颈。

## 11. 如何定义结果，避免只有 ASR

主结果是每个任务运行中是否出现已实际发生的任务外效果，并同时报告合法任务完成率。另记录效果类型、受影响资源、调用尝试、实际提交和告警。对于不可撤回效果，最终状态恢复不能抹去历史记录。

需要单独统计四类失败：

1. 主模型提出任务外操作。
2. guard 收到了该调用但错误允许。
3. guard 未被调用，或者收到错误/未解析的参数。
4. guard 拒绝后，效果仍然发生。

第 2 类是主要研究对象；第 3/4 类通常先按已知集成或执行问题处理，不混成“语义防护退化”。已知模式的实际频率仍可报告，但不足以独立支撑本文 novelty。

为避免把架构本身变化误认为防护退化，可以计算：

```text
L(a, g) = 架构 a、guard 设置 g 下发生违规效果的运行比例

guard 收益 B(a, g) = L(a, G0) - L(a, g)

迁移后的收益变化 = B(优化执行, G1) - B(S, G1)
适配恢复量       = L(优化执行, G1) - L(优化执行, G2)
```

这些是配对实验的整体效应对比。它们本身不能证明机制，仍需层 A 及信息消融。出现零违规的地板效应时，不应硬解释 guard 收益变化。

还要报告：clean/attack 下的 task utility、安全且成功完成的比例、对独立合法提案的误拒、主模型与 guard 各自 token/latency，以及重试和失败的花费。

统计上以任务为主要独立单位，必要时按 repository 聚类；重复 seed 是任务内部重复。正式规模由 pilot 的差异与变异决定，主分析给出效应大小和置信区间。不要用任意数量任务或单个 p 值证明“足够发论文”。

## 12. 任务怎么选，才不显得刻意造例子

先按任务语义选样本，而不是按攻击成功情况选。

| 任务层 | 例子 | 用途 |
|---|---|---|
| 固定目标、外部内容只填正文 | 用户指定位置的汇总报告 | 简单权限往往足够，提供稳定迁移对照 |
| 动态目标，但有独立可信约束 | 根据返回 ID 查询资源，目标必须属于指定项目 | 检查实际参数与可信约束是否都可见 |
| 需要上下文判断的修改 | 修复指定行为，允许必要跨模块修改，禁止削弱既有安全约束 | 测语义 guard 的误放行和误拒，人工 oracle 成本更高 |
| 正常任务本身包含敏感操作 | 用户明确授权特定配置更新 | 防止一个“永远拒绝写入”的设置被评为最佳 |

同一任务尽量保留 clean、恶意指令、等长良性说明；可信用户明确授权目标行为的正对照用于验证判定能力，但它改变了 task，不能冒充相同 task 的纯来源干预。

主攻击由非可信文件或工具返回内容承载，不能修改可信用户任务、guard、权限规则或执行代码。首轮将普通字符串指令与恶意结构化参数分开统计。无模型参与时就能直接产生目标效果的脚本，不计为本研究的 IPI 证据。

## 13. 实现范围保持小，复用什么与不做什么

优先复用 AgentDojo 的任务状态和判定、一个公开执行 runtime、一个可固定的语义 guard。D 使用现成结果引用或已有程序化工具运行能力。具体工具版本、原生 hook 和可观测信息先做小样本适配审查，本稿没有宣称这些组合已经跑通。

第二个 runtime 用于关键关系复验，不要求起步就兼容所有框架。支持程序化子调用检查的实现是重要候选；不支持同权限切换的系统只能作为生态案例，不能放进纯因果对照。

只加必要的事件日志与少量实验适配。无需开发新语言、完整防护平台、能力等价系统、manifest 验证、签名证据链或自动冻结流程。也不恢复已放弃的 RP 路线。

仓库环境中的功能评分可复用官方 SWE-bench harness，但安全判定独立存在；不能把所有维护任务强塞入 SWE-bench，也不能重写其功能评分器。

## 14. 两周最小实验与可执行的停止条件

### 第 1—3 天：先确认现实迁移是否存在

检查两个公开 runtime 的调用与 guard 接口，用正常任务记录主模型和 guard 实际可见的信息。确认子调用检查没有被漏接；确认 D 没有新文件/网络权限；明确无效配置。

这一步需要得到至少一种真实部署路径：执行优化会改变 transcript-based guard 的可见信息。若两个候选实现都完整保留信息且无明显代价，不能自行删信息制造退化；转而验证成功迁移的条件，或停止本主张。

### 第 4—6 天：做小规模配对审查

选 8 个任务，开发与留出任务各 4 个，涵盖上述不同语义。用少量正常及受攻击运行收集提案，建立合法性标签。先运行层 A，判断 G1/G2 是否有超出采样噪声的差异，检查等长无关信息对照。

只在开发集确定 guard 输入规则与提示词；不能看完留出效果再改规则，然后把同一批结果当确认性证据。

### 第 7—10 天：跑端到端 pilot

一个模型的起始规模可以是：

```text
8 tasks × 3 execution modes × 3 guard settings
        × 2 conditions（clean / attack）× 2 repeats = 288 runs
```

配对审查、确定性策略对照和第二模型复验另计。这个数字只用于估计工期，不代表有足够统计功效。先用少量运行估算真实费用，若环境适配耗时过多，缩小 pilot，不能削弱权限和判定来追进度。

### 继续完整研究需要什么

- 在留出任务上出现可重现的关系，而不只是一条漂亮轨迹。
- 原因能由固定调用审查或单因素消融支持，而非漏检查、取消失败或额外工具能力。
- 至少一种实际执行接入支持该机制；第二模型或 runtime 复验没有把它完全推翻。
- 改进安全性时合法任务仍可完成，适配成本没有被隐藏。
- 与 PACT、ClawSentry、ToolGuardian 等的细读比较后，仍有新的迁移结论，而非复述来源与上下文的重要性。

这些是研究推进标准，不是机械的统计显著性阈值。

### 应停止或改题的情况

- 所有差异都来自刻意不给 guard 它原本支持的信息。
- 只发现 Stop Means Stop 已覆盖的停止/并行泄漏，没有其他新经验知识。
- 对齐实际参数与检查位置后，所谓语义退化消失；这只剩一个普通集成修复。
- 一条简单静态策略在所有有意义任务上都能无损解决问题，剩余复杂设计没有价值。
- G2 的提升仅靠额外 token，等长对照也一样有效，或费用完全吃掉优化收益。
- 只有合成 toy case 有结果，实际任务没有自然出现对应条件。

零差异并不自动是坏结果，但如果只确认“正确接入的逐调用 guard 不受调度影响”这一已有预期，通常不足以单独支撑强论文。不能靠继续扩样本包装贡献。

## 15. 实用交付物与候选论文贡献

开发者最终应拿到一张有实验依据的迁移建议表，而不是笼统结论“多工具不安全”。例如：某类优化可直接采用；某类需要把实际子调用与相关事件交给 guard；某类保留防护后并无成本优势。具体条目必须由结果决定。

可复用产出是少量代表性任务、事件级判定、失败与成功迁移案例，以及可在已有测试流程中运行的回归用例。它们服务于论文结论，不以新建平台作为卖点。

候选 Introduction claims：

1. **[Needs validation]** We measure whether the security benefit of existing safeguards transfers from step-wise tool use to parallel and dependent execution under matched tools, permissions, and per-call mediation.
2. **[Needs validation]** We separate changes in agent proposals from changes in safeguard decisions using paired, pre-execution evidence views and end-to-end evaluations.
3. **[Needs validation]** We identify and replicate the workflow conditions under which execution optimizations preserve, degrade, or improve protection, while distinguishing semantic failures from known enforcement defects.
4. **[Needs validation]** We evaluate whether runtime evidence already available at tool boundaries can preserve protection without restoring all intermediate observations to the main model, quantifying the resulting utility and cost tradeoffs.

不声称“首次跨架构防护”“新信息流理论”“通用安全保证”或“保证发表一区”。

## 16. 投稿强度的诚实判断

这比原先的三组 ASR 比较更有希望，因为它对应真实的软件迁移决定、有可独立检验的机制、有可落实的结果。但它目前仍是提案。

面向高水平 SE 期刊或会议，强版本需要公开 runtime 与真实工作流上的新经验结论、可靠因果分解、合法任务与成本评估、可复用测试案例。若只有一个自建 guard 加 AgentDojo 排行榜，强度仍不够。

面向安全顶会，还需要更强的真实边界影响、可推广的安全结论或实质技术贡献；“跨设置评估得更全面”不能自动满足要求。期刊分区依具体体系、年份和类别判断，本稿不作未核实的一区名单承诺。

**给导师的简短介绍：**

我们研究 agent 应用从逐步调用升级到多工具执行时，既有防护能否保留效果。首先固定工具权限和逐调用检查，区分模型提出了不同操作，还是相同审查器因为可见信息变化而判断不同。然后验证能否让主模型继续少看中间结果，同时给审查器保留必要的运行信息，从而维持安全性并保留性能收益。贡献取决于真实系统中的迁移规律及原因；如果只复现已知取消漏洞、丢来源信息或简单权限漏接，就停止这条主线。
