# Proposal A：一次决定连续执行多个工具，会怎样改变 Agent 的安全风险？

这份提案想回答一个实际的系统设计问题：让 agent 一次安排更多工作，可以节省等待和模型调用，但会不会改变它被攻击的机会，以及攻击成功后的损失？

论文希望通过实验给出两类知识：**风险往哪个方向变化，以及这个结论在什么条件下成立。** 目前这些都是研究问题，尚无本项目的实验结果。相关文献沿用 2026 年 9 月 22 日的选题调研；本文只展开 Proposal A。

## 1. 先用一个例子说明问题

假设用户让一个 coding agent 修复插件中的一个小问题。它需要搜索代码、读文件、修改实现，再运行测试。

最常见的一种做法是：模型先决定读哪个文件，看到结果后，再决定下一步。整个过程可以写成：

```text
决定读文件 → 看到内容 → 决定下一步 → 执行 → 再看结果
```

另一种做法是：模型一次安排一组操作。例如，同时读取几个文件，或者先搜索文件，再根据搜索结果读取相关内容，最后把整理好的结果交回来。

```text
决定一组操作 → 工具连续或并行执行 → 返回整理后的结果
```

现在，某个文件的注释里被放入了一段恶意指令，试图让 agent 关闭一个与当前任务无关的安全检查。这里讨论的是 agent 把文件里的文字当成指令来执行，而不是文件本身包含能直接运行的恶意代码。

两种执行方式可能产生不同结果。

如果每读一个文件都把完整内容送给模型，模型可能较早接触到恶意指令。如果工具在本地只提取任务需要的字段，恶意段落可能根本不会进入模型上下文。这时，一组操作一起执行可能减少受攻击的机会。

但如果模型在安排这组操作之前就已经被带偏，它也可能一次安排多项不该发生的修改。后面的操作会不会继续执行，取决于系统中途有没有真正能拦住它的检查。

这两个过程值得分开研究：一个关系到“是否被带偏”，另一个关系到“被带偏之后会发生什么”。

这个例子只用于说明机制。正式实验还要证明：正常任务确实会读到该内容，目标修改确实不在用户授权范围内，而且攻击者无法直接完成这项修改。

## 2. 论文具体研究什么

拟定研究问题：

> 当 agent 从一步一反馈，变成一次决定后连续执行多个工具时，外部内容进入模型的时机、系统阻止错误操作的机会，以及最终损失会怎样变化？

这里需要分清四个时刻。

| 时刻 | 通俗解释 | 为什么要分清 |
|---|---|---|
| 模型作出决定 | 模型说“接下来做这些事” | 一次决定可能安排一项，也可能安排很多项操作 |
| 模型看到结果 | 文件、网页或工具返回值进入模型上下文 | 恶意文字通常要在这里被某个模型读到，才有机会改变它的判断 |
| 系统检查授权 | 程序或人判断“这项具体操作现在允许吗” | 工具有权限被调用，不代表它的每个目标、参数都获得授权 |
| 操作实际生效 | 文件被修改、消息被发送、配置被更新 | 此时损失可能已经发生；后面发现问题未必来得及撤回 |

这四个时刻不一定紧挨着。一组操作可以只在开始前检查，也可以在每次实际写入前检查；工具结果可以立即交给模型，也可以等整组执行完再返回。

还要特别注意：让同一个模型多思考一次，不等于多了一道可靠的安全检查。模型可能继续相信刚才的恶意指令。只有能识别并阻止相关效果的机制，才算这里讨论的有效检查。

## 3. 为什么风险可能一升一降

### 更少看到恶意内容，可能更难被带偏

有些任务只需要一个返回值，不需要让模型阅读整份材料。例如，工具可以从一组记录里取出状态字段，再把结果汇总给模型。原始内容中的恶意文字如果没有进入模型，就少了一条影响决策的路径。

这是一个待验证的假设。它成立需要几个条件：本地处理确实没有把恶意部分送回模型；过程中没有另一个模型替它阅读原文；任务仍然正常完成。

如果所谓“合并执行”只是把十份原始结果一次性全部塞进上下文，风险未必下降。模型调用次数少了，不代表它看到的恶意内容少了。减少反馈也可能隐藏异常线索，让模型更难发现问题。

### 决定已经出错时，损失可能更大

模型可能在看到恶意内容后，安排了一串任务外操作。如果执行程序不断往下运行，而且后续操作之间没有有效检查，就可能在被阻止前影响更多资源。

这同样是待验证的假设。逐步执行也可能一直犯错；一次 shell 调用本来就能做很多事；准确的逐项授权检查也可能把两种执行方式都拦住。因此，不能只凭“这次 action 包含更多调用”就推断损失更大。

真正需要测量的是：在总工作预算相同、工具能力相同的情况下，某种执行方式是否让更多任务外效果在被阻止前实际发生，以及整项任务结束时损失是否仍然更多。

### 两个过程可能同时存在

一种架构可能较少被成功攻击，但一旦被攻击成功，后果更重。如果只报告攻击成功率，就会漏掉后一部分。

论文可以分别报告发生违规的概率、违规时影响的资源范围，以及所有运行的平均损失。损失难以统一计价时，就分别记录修改了多少受保护资源、是否发送了任务外请求、是否破坏了安全行为，不强行压成一个分数。

我们希望观察到风险变化的条件，并不预设一定会出现上述反转。没有反转、只有稳定的单向效果，也可能有价值，前提是它有清楚的解释且超出已有工作的结论。

## 4. “边界条件”具体指什么

这里的边界条件，就是一句结论成立所需要的前提。例如，“减少中间反馈能提高安全性”太宽泛；“在只需提取固定字段、没有内部模型且字段不控制敏感操作的任务中，减少原文回传降低了语义注入成功率”才是可以检验的结论。

下面这些条件最值得检查。

| 条件 | 可能改变结论的原因 |
|---|---|
| 攻击内容是在计划之前，还是执行过程中出现 | 前者可能影响整份计划；后者能影响什么，要看后续还有没有模型决策或数据传递 |
| 后续操作的参数是否已经确定 | 已经确定的参数，不会仅仅因为某个工具返回了恶意文字就自动改变 |
| 中间结果是否交给某个模型 | 外层模型没看到，不代表内部的摘要模型或子 agent 没看到 |
| 返回值被用作普通内容，还是文件路径、命令、收件人等参数 | 同一个值进入不同位置，能够造成的效果差别很大 |
| 检查发生在整组开始前，还是具体操作生效前 | 动态算出的目标可能只有到后面才能被准确检查 |
| 发现问题后能否取消后续操作 | 已经发出的并行请求可能无法撤回；“检测到了”不等于“损失被阻止了” |
| 工具之间是否共享状态 | 即使没有模型重新决策，先发生的写入也可能改变后面的执行结果 |

其中有些结论不需要靠大量实验发现。例如，一份固定计划里没有内部模型，也没有把文本当代码执行的路径，那么返回文本中的“忽略之前的指令”不会自行改写这份计划。这是执行方式本身决定的。

但工具返回的恶意地址、路径等数据，仍可能被传给后续工具。这属于数据被错误使用的路径，要与“模型被文字说服”分别记录。否则论文会把不同原因混在一起。

## 5. 与已有工作相比，论文还需要贡献什么

已有研究已经讨论了跨工具攻击、信息流控制和权限检查。这篇论文不能把“多个工具组合起来有风险”当成新发现。

[Les Dissonances](https://www.ndss-symposium.org/ndss-paper/les-dissonances-cross-tool-harvesting-and-polluting-in-pool-of-tools-empowered-llm-agents/) 已研究工具池中的跨工具攻击；[ChainFuzzer](https://arxiv.org/abs/2603.12614) 研究跨调用的数据依赖与漏洞路径。它们直接限制了“首次研究 multi-tool security”这种说法。

[CaMeL](https://floriantramer.com/publications/camel25/) 和 [FIDES](https://www.microsoft.com/en-us/research/publication/securing-ai-agents-with-information-flow-control/) 已经研究如何隔离不可信内容、约束信息流。[Progent](https://arxiv.org/abs/2504.11703) 则是任务权限控制的重要近邻。因此，“少接触不可信文字”和“每次操作检查权限”也不能单独作为新思想。

候选空间在于：在可比较的条件下，把执行方式带来的几个变化拆开，测清它们分别起什么作用，再去真实系统里验证。例如，某种方式降低了首次违规的概率，却增加了少数失败运行的损失；这种差异究竟来自信息过滤、参数传递，还是检测后无法取消已启动操作？

前一份调研没有定位到完整匹配这一设计的研究，但这只是检索范围内的判断。定题时仍需继续核查最接近的工作。即使没有完全一样的对照实验，也必须证明结果能提供新的解释或帮助工程师作出不同的设计选择。

## 6. 四个可以直接用于论文的研究问题

### RQ1：执行方式会怎样改变首次被攻击成功的机会？

比较不同方式下，恶意内容是否被模型看到、何时被看到，以及随后是否出现任务外操作。同步检查正常任务完成率，避免把“什么都做不了”误判成安全。

### RQ2：一次错误决定会造成多大后果？

统计下一次有效检查前已经发生的任务外效果，以及任务结束时的总损失。检查真正阻止了后续动作，还是只是在损失发生后发出告警。

这里不能只挑各组中攻击成功的运行直接比较，再声称差异完全由架构造成。不同架构可能是在不同难度的样本上失败。需要补充共同攻击入口、固定计划等对照。

### RQ3：哪些条件会改变风险的方向？

按预先确定的条件比较：只读操作、读后修改、读后运行命令；参数固定或依赖返回值；有无内部模型；检查与取消发生在何处。目标是解释某个结果何时成立、何时失效。

### RQ4：节省的时间和成本，是否值得承担对应风险？

同时报告合法任务完成率、实际损失、模型调用次数、耗时和 token 消耗。最终可能得到几种适合不同任务的选择，而不是宣布一个全局最安全的架构。

## 7. 实验怎样做，结论才站得住

第一轮比较三种执行方式即可。

| 方式 | 模型如何安排工作 |
|---|---|
| 逐步执行 | 每次调用一个工具，收到结果后再决定 |
| 并行执行 | 一次安排多个独立调用；需要依赖结果时仍进入下一轮 |
| 依赖式执行 | 一次安排一串有依赖的调用，后续工具可以使用前面返回的值 |

暂时不加入自动学习、进化或持久复用的新工具。这些因素会增加需要解释的问题。也不开发新的受限编程语言。

三组使用相同模型、任务、底层工具、权限规则、攻击来源和总预算。一次外层调用里藏了多个底层操作，也照样计入预算。不能只限制模型轮数，否则一组可能免费多做很多工作。

模型面对不同接口，可能会制定不同计划。这是实际使用该接口的整体效果，但不足以解释原因。因此需要两类实验：先让模型自然完成任务，看最终差异；再固定计划或固定工具结果，只改变某一个因素，检查差异是否跟着变化。

例如，固定同一批工具结果，比较完整回传和只回传必要字段；固定相同独立操作，比较顺序执行和并行执行。每次只回答一个具体问题，避免把所有变化都归到“multi-tool”上。

权限检查的位置也应单独处理。主比较保持一致；如果另做“整组检查”和“逐项检查”的对照，就明确说这是在研究检查位置。不能暗中给某组更弱的防护，再宣称它的执行方式更危险。

实验分两种攻击时序：一种让恶意内容在执行过程中首次出现；另一种让模型在安排下一组操作前先接触同一段恶意内容。后者只保证它看到了攻击，不保证它已经被成功带偏。

底座可以先用 [AgentDojo](https://github.com/ethz-spylab/agentdojo)，复用已有任务与成功判定，再补效果和时间日志。依赖执行可以参考 [LLMCompiler](https://github.com/SqueezeAILab/LLMCompiler)。这些选择仍需先验证能否满足公平对照，不能仅凭有公开代码就认定可以直接组合。

若希望面向 FSE、ICSE 等软件工程会议，后续至少需要一组真实仓库任务验证核心机制。AgentDojo 上的结果可以帮助定位问题，但还不能直接说明 coding agent 中也存在同样规律。

## 8. 最后能写进论文的贡献是什么

目前可以提出以下四项候选贡献，全部需要实验验证。

1. **解释风险变化的原因。** 分清减少恶意内容暴露与扩大错误执行后果这两个过程，并用对照实验检查它们是否分别存在。
2. **给出结论适用的条件。** 说明在什么任务、参数传递和检查方式下，一种执行方式风险更低；在哪些条件下优势消失，或者排序反转。
3. **补充攻击成功率之外的证据。** 同时记录实际受影响的资源、被阻止前发生的效果，以及正常工作的完成情况，让少数但损失较大的失败也能被看见。
4. **提供经过验证的系统设计建议。** 把实验结果落实到中间结果是否回传、敏感操作何时检查、检测后如何取消等具体选择上，并在真实执行系统中复验。

“经验知识”可以这样理解：最终论文应当能写出一句有范围、有证据的结论，并让读者知道为什么可以相信它。

例如，下面只是预期结论的写法，不是已经得到的结果：

> 在我们测试的固定字段提取任务中，减少原始返回内容进入模型，降低了语义注入成功率，同时保留了任务完成能力；但这一优势不适用于返回值直接决定敏感操作目标的任务。

或者：

> 在已出现错误计划的运行中，检测后仍继续完成的并行操作解释了额外损失；加入可取消的执行边界后，这部分差异缩小。

这样的结论必须有配对数据、误差范围和具体轨迹支撑。即使结果与预期相反，也应按证据改写贡献，而不是为了保留故事挑选实验。

## 9. 先用两周判断值不值得继续

第一周先选一小组任务，让三种执行方式都能正常完成。任务中既有独立读取，也有读取后执行敏感操作。验证攻击入口和禁止效果的判定，再接好模型观察、工具执行与实际效果的日志。

第二周做小规模配对实验。同一任务分别运行无攻击、执行中遇到攻击、决策前遇到攻击三种条件。可以从 12 个任务、每种条件重复 3 次开始：三种架构合计 324 次运行。这只是工作量估计，不是证明样本量足够。环境适配和费用也需先用少量运行估计。

每个任务都要看完整过程：有没有接触攻击、有没有完成正常工作、哪里首次出错、错误操作是否被拦截。重复运行能观察随机性，但不能把同一个任务的多次运行当成很多独立任务。

值得继续的信号包括：在多个任务上出现稳定且能解释的风险差异；单独改变观察或取消机制后，差异随之变化；在另一个模型或真实执行系统中仍能复现；正常任务能力没有因为接口难用而大幅下降。

如果差异完全来自某组做了更多工作、权限更大，或模型根本不会使用另一种接口，就先修正实验。若修正后只剩调用次数造成的机械增长，这条主张不值得继续扩大。

如果准确而简单的逐项授权检查消除了全部差异，也应该接受这个结果。接下来可以判断它是否揭示了真实系统中有价值的适用条件；如果只是再次确认已知原则，就不必为了凑论文继续增加任务。

零攻击成功也需要解释。先确认攻击被实际读到、正常任务能完成、正对照有效，再讨论该条件下的安全性。一个小规模 pilot 不能证明系统普遍安全。

## 10. 与导师讨论时，可以这样介绍

我想研究 agent 一次决定后连续执行多个工具，会怎样改变安全风险。重点放在两个过程：中间内容较少进入模型，是否让攻击更难影响决策；如果决定已经出错，连续执行是否会在被阻止前造成更多任务外效果。

我准备先固定模型、工具、权限和总预算，比较逐步、并行和依赖式执行。整体运行看真实差异，固定计划和固定观察的对照用来解释原因。之后再用真实代码仓库任务验证主要发现。

预期论文贡献是风险变化的规律和适用条件，例如什么场景可以减少中间反馈，什么位置需要在具体操作生效前检查，以及检测后无法取消会造成什么后果。目前还不能承诺这些规律一定存在。两周 pilot 的任务就是检验它们是否超出已有信息流和权限控制工作的结论，再决定要不要投入完整研究。
